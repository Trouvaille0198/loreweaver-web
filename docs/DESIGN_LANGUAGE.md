# Loreweaver 设计语言

本文定义 Loreweaver Web 的产品气质与视觉判断标准。它回答“页面应该给人什么感受、信息为什么这样排、出现新需求时如何延续同一种审美”。具体组件 API、代码归属和提交检查见 [FRONTEND_GUIDELINES.md](./FRONTEND_GUIDELINES.md)。

## 1. 产品气质

Loreweaver 是一张安静、可信、适合长时间阅读的数字牌桌。界面服务于叙事、角色与协作，不与内容争夺注意力。

设计关键词：

- **叙事优先**：故事、角色和当前行动永远比应用外壳更醒目。
- **温暖克制**：Lamplight 的近黑、羊皮纸与黄铜感构成品牌基调，但不堆砌仿古纹理和奇幻装饰。
- **清晰耐读**：长时间游戏需要稳定的行长、节奏和对比度，而不是追求瞬间刺激。
- **轻触感**：边界、阴影和位移让控件有触感，效果保持短促、低调。
- **系统可信**：状态、权限、危险操作和异步反馈必须明确，不让用户猜测。

### 1.1 应该像什么

一张整理得当的主持人桌面：纸张有层次，工具各归其位，灯光温和，故事位于视线中心。

### 1.2 不应该像什么

| 避免的方向         | 原因                                                           |
| ------------------ | -------------------------------------------------------------- |
| 通用 SaaS 后台     | 大片冷灰、密集数据卡和同权重按钮会削弱牌桌气质                 |
| 游戏商城或赌场界面 | 高饱和渐变、发光边框和奖励式动效会抢夺叙事注意力               |
| 伪古董装饰         | 羊皮纸纹理、卷轴边框、哥特花体会降低可读性，也难以适配五套主题 |
| 终端模拟器         | DF-16 与 Phosphor 是配色主题，不代表所有布局都应退化为字符界面 |
| 卡片瀑布           | 不是每段文字都需要一层边框；卡片只表达真实的信息分组           |

## 2. 视觉层级

页面依靠表面、间距和排版建立层级，不靠任意颜色或装饰线。

```text
应用画布 surface-canvas
├─ 页面外壳 app header / ScreenShell
│  ├─ 页面标题
│  └─ 页面正文
│     ├─ 一级内容面 Surface
│     │  ├─ SectionHeader
│     │  └─ 内嵌区域 surface-inset
│     └─ 浮层 / 抽屉 surface-2 + shadow-md/lg
```

| 层级   | 用途                             | 视觉处理                                     |
| ------ | -------------------------------- | -------------------------------------------- |
| 画布   | 整个应用背景                     | 主题底色与极弱的品牌色径向光，不放内容边框   |
| 页面   | 一个完整任务                     | `ScreenShell` 控制标题、返回、宽度与错误状态 |
| 内容面 | 一个可以被命名的信息组           | `Surface`，使用一层边界和 `shadow-sm`        |
| 内嵌区 | 内容面中的预览、字段组、次级列表 | `surface-inset`，阴影弱于父层                |
| 浮层   | 菜单、模态框、手机抽屉           | 比页面更高的表面与阴影，必须有明确关闭路径   |

同一视觉区域最多出现三层表面。出现“卡片套卡片再套卡片”时，应重新梳理信息结构。

## 3. 色彩与主题

### 3.1 两级令牌

主题色板只存在于 `src/lib/themes.ts` 的 `--lw-*` 原始令牌。组件只读取 `src/design-system.css` 派生出的语义令牌：

- 表面：`--surface-canvas`、`--surface-1`、`--surface-2`、`--surface-inset`、`--surface-hover`
- 边界：`--line-subtle`、`--line-default`、`--line-strong`
- 文本：`--text-primary`、`--text-secondary`、`--text-tertiary`、`--text-accent`
- 状态：`--lw-success`、`--lw-fail`、`--lw-fumble` 以及角色语义色

组件不得根据主题名编写分支，也不得用固定十六进制颜色补救某一套主题。

### 3.2 五套主题的角色

| 主题       | 气质                                         | 设计检查重点                                         |
| ---------- | -------------------------------------------- | ---------------------------------------------------- |
| Lamplight  | 默认品牌主题，近黑画布、羊皮纸文字、黄铜强调 | 温暖但不能发黄发糊；正文对比必须稳定                 |
| Amber      | 更强烈的琥珀终端感                           | 控制强调色面积，避免整页橙色                         |
| DF-16      | 高对比的经典 16 色感                         | 依然保留圆角、空间和层级，不模拟低分辨率终端         |
| Phosphor   | 深绿荧光气质                                 | 黄色强调只用于动作和焦点，避免大面积荧光             |
| Paperwhite | 纸张感浅色主题                               | 边界不能过淡，阴影不能显脏，文字不能使用透明黑凑层级 |

### 3.3 强调色预算

- 一个视口内只允许一个主要动作拥有实心强调色。
- 当前选择可使用浅色强调背景与强调边界，不与主要动作争夺权重。
- 大面积背景不使用强调色；品牌色只承担焦点、选择、关键动作和少量环境光。
- 成功、警告、危险必须使用各自的语义色，不能全部借用强调色。
- 状态不能只靠颜色表达，必须同时有文字、图标、形状或 `aria-*` 状态。

## 4. 排版

Loreweaver 使用三类字体角色：

| 字体令牌       | 用途                              | 禁止用途           |
| -------------- | --------------------------------- | ------------------ |
| `--font-story` | 页面标题、章节标题、叙事正文      | 密集表单、微型标签 |
| `--font-ui`    | 按钮、字段、导航、说明、表格      | 代码、密钥、协议值 |
| `--font-mono`  | 命令、密钥、URL、数值读数、快捷键 | 长篇说明和普通标题 |

推荐层级：

| 文本角色 | 尺寸与行高           | 规则                             |
| -------- | -------------------- | -------------------------------- |
| 页面标题 | `24–32px / 1.15–1.2` | 使用 story 字体，只出现一次      |
| 区域标题 | `16–20px / 1.25`     | 简短名词短语，不加句号           |
| 卡片标题 | `13–15px / 1.35`     | UI 字体，600–650 字重            |
| 正文     | `14–16px / 1.6–1.75` | 叙事可更宽松，控件说明保持紧凑   |
| 辅助说明 | `12–13px / 1.5–1.6`  | 只说明后果、格式、例外或恢复方式 |
| 微型标签 | `10–11px / 1.3–1.4`  | 仅用于分组、快捷键、状态元信息   |

排版原则：

- 标题与正文靠字号、字重和留白区分，不依赖全大写。
- 分组标签允许全大写，但只使用微型字号和较宽字距。
- 一行文字尽量不超过 `68ch`；叙事栏由用户设置在 `60–140ch` 之间。
- 数值需要比较时使用等宽字体；普通内容不要为了“技术感”使用等宽字体。
- 中文与英文共用相同层级，不针对语言调整组件高度或写独立布局。

## 5. 间距与几何

### 5.1 间距阶梯

只使用统一的 4px 阶梯：

| 令牌         |   值 | 常见用途               |
| ------------ | ---: | ---------------------- |
| `--space-1`  |  4px | 图标内部、紧密元信息   |
| `--space-2`  |  8px | 按钮图标间距、紧密列表 |
| `--space-3`  | 12px | 字段内部、紧凑卡片     |
| `--space-4`  | 16px | 手机卡片、同组控件     |
| `--space-5`  | 20px | 标准卡片内边距         |
| `--space-6`  | 24px | 页面一级节奏           |
| `--space-8`  | 32px | 双栏间距、区块分隔     |
| `--space-10` | 40px | 空状态、宽松页面留白   |
| `--space-12` | 48px | 桌面页面外边距上限     |

判断顺序：先确定信息是否同组，再选择间距。不要用随机 `margin` 修补结构；同级排列优先由父级 `gap` 管理。

### 5.2 圆角

| 令牌            |    值 | 用途                     |
| --------------- | ----: | ------------------------ |
| `--radius-sm`   |   7px | 小按钮、微型控件         |
| `--radius-md`   |  10px | 输入框、标准按钮、内嵌区 |
| `--radius-lg`   |  14px | 卡片、设置导航           |
| `--radius-xl`   |  20px | 主要连接卡、显著浮层     |
| `--radius-pill` | 999px | 状态胶囊、读数、圆点标签 |

父子表面的圆角必须递减。标准卡片内的字段使用 `radius-md`，不要与父卡片同样圆润。

### 5.3 阴影

- `shadow-sm`：卡片与普通内容面。
- `shadow-md`：下拉菜单、抽屉、悬停中的重要卡片。
- `shadow-lg`：模态框和最高层浮层。
- 同一表面不叠加多套阴影；浅色主题下优先依靠边界，阴影只表达高度。

## 6. 组件的视觉语义

### 6.1 Button

| 变体        | 何时使用                         | 视觉权重                   |
| ----------- | -------------------------------- | -------------------------- |
| `primary`   | 当前区域唯一的主要提交或继续动作 | 最高，实心强调色           |
| `secondary` | 普通、可逆且需要明确可见的动作   | 中等，实体表面与边界       |
| `quiet`     | 返回、取消、展开、复制、次级工具 | 低，默认透明               |
| `danger`    | 删除、重置和不可逆动作           | 危险语义，不伪装成主按钮   |
| `success`   | 启动或明确完成的正向动作         | 仅在成功语义真实存在时使用 |

按钮文案使用动作动词。一个卡片中如果出现多个 `primary`，说明任务层级还没有梳理清楚。

### 6.2 Surface 与 SectionHeader

- `Surface` 表达一个可以被用户命名的信息组，而不是单纯给内容加框。
- `SectionHeader` 负责标题、必要说明和右侧动作的稳定对齐。
- 标准内容面使用 `default`；内嵌信息使用 `subtle`；当前核心对象使用 `accent`；危险区域使用 `danger`。
- 卡片之间使用页面间距，卡片内部使用组件间距，不用 `<hr>` 连续切割。

### 6.3 Field

- 标签始终可见，placeholder 只展示格式示例。
- 说明位于控件下方，只解释输入格式、影响范围或限制。
- 错误紧邻字段并建立 `aria-describedby` 关系。
- 同一行只并排放置强相关、可同时理解的字段；手机端恢复单列。

### 6.4 Notice 与 EmptyState

- `Notice` 用于用户需要立即理解的状态变化，不用于普通说明。
- 错误使用 `role="alert"`；非阻塞结果使用 `role="status"`。
- 空状态说明“这里为什么为空”和“用户下一步能做什么”；没有下一步时只保留事实。
- 空状态不添加欢迎语、格言、产品宣传或情绪化导语。

### 6.5 列表、表格与卡片

- 可比较的列式数据使用表格；需要扫读标题和状态的对象使用列表；需要独立操作和说明的对象使用卡片。
- 不为了视觉丰富把表格改成重复卡片。
- 当前项同时使用边界、浅背景和 `aria-selected`/`aria-pressed`，不只改变文字颜色。
- 行内操作默认为 `sm quiet`；删除操作使用 `sm danger`。

## 7. 页面原型

### 7.1 连接页

目标是让用户完成一次明确的加入动作。

- 只保留连接所需字段和一个主要按钮。
- 状态位于标题旁，错误位于表单附近。
- 桌面内容宽而不散，手机保持单卡片和 16px 外边距。
- 连接前保留语言选择；进入牌桌后，语言归入设置。

### 7.2 牌桌页

目标是让叙事成为首页，而不是先展示菜单或仪表盘。

- 叙事栏占据主要视线，工具退到顶栏、输入坞和右侧桌面。
- 长期可见的状态必须紧凑；偶发工具使用 popover、抽屉或菜单。
- 手机端桌面区变为底部抽屉，入口靠近输入区，避免把主要动作放在拇指难以触及的顶部。

### 7.3 设置工作区

```text
桌面 ≥ 761px
┌──────────────┬────────────────────────────────────┐
│ 分组导航      │ 当前设置区域                        │
│  当前项       │ ┌ Surface ──────────────────────┐ │
│  其他项       │ │ SectionHeader       可选动作   │ │
│              │ │ 内容 / 字段 / 预览              │ │
│              │ └────────────────────────────────┘ │
└──────────────┴────────────────────────────────────┘

手机 ≤ 760px
┌ 横向可滚动页签 ───────────────────────────────────┐
├ 当前设置区域，单列卡片                              ┤
└────────────────────────────────────────────────────┘
```

- 设置页统一使用 `SettingsWorkspace`，不复制侧栏或页签实现。
- 导航按用户任务分组，不按代码模块分组。
- 当前区域标题与导航名称一致，不添加营销式副标题。
- 即时生效的偏好不放“保存”按钮；远端配置提交必须有明确动作。
- 桌面侧栏保持稳定，手机页签可滚动且不造成页面横向溢出。

### 7.4 管理与危险操作页

- 普通管理页宽度不超过 `920px`；多栏工作区不超过 `1200px`。
- 列表在左、详情在右时，详情必须能够独立命名；手机转为顺序浏览或独立页面。
- 可保存配置采用“目录 + 编辑器”结构：桌面并列展示已有对象与当前编辑对象，`920px` 以下按目录、编辑器的顺序转为单列。
- 目录行只承载识别、选择和短操作；字段集中在编辑器中，不把每个配置展开成完整表单。
- 已保存对象的身份字段保持稳定。创建另一身份使用明确的新建入口，避免一次保存同时表达重命名与新增。
- 危险操作集中在清晰的危险区域，与日常操作保持距离。
- 删除房间、重置战役等操作要求输入对象名称确认，不使用含糊的“确定吗”。

### 7.5 弹层与抽屉

- Popover 用于短列表和即时选择；模态框用于必须先完成或取消的集中任务；手机抽屉用于保留当前上下文的工具区。
- Escape、关闭按钮和点击遮罩的行为保持一致。
- 关闭后焦点返回触发器；弹层内不能形成键盘陷阱。

## 8. 交互与动效

| 状态     | 处理方式                                                   |
| -------- | ---------------------------------------------------------- |
| Hover    | 轻微表面、文字或边界变化；密集列表与表单控件不产生位移     |
| Active   | 回到原位，产生按下感                                       |
| Focus    | 统一 `--focus-ring`，不能用 `outline: none` 后不补焦点样式 |
| Disabled | 保持可辨识，降低透明度并使用原生 `disabled`                |
| Loading  | 禁用重复提交，显示 spinner 或明确的进行中文案              |
| Success  | 紧邻动作区域反馈，不用全屏庆祝动效                         |
| Error    | 说明发生了什么和可执行的恢复动作，不能只显示错误码         |

- 微交互使用 `120ms`，面板进入和表面变化使用 `180ms`。
- 动画曲线使用 `--ease-out`，不使用弹簧、回弹或持续漂浮。
- `prefers-reduced-motion: reduce` 下取消非必要变换和动画。
- 导航页签支持方向键、`Home`、`End`；选择后焦点跟随当前页签。

## 9. 文案规则

界面文字必须帮助用户完成任务，不承担气氛营造。

### 9.1 可以出现的说明

仅在至少回答一个问题时保留说明：

1. 这个操作会影响什么？
2. 输入需要什么格式？
3. 存在什么不明显的限制或例外？
4. 出错后如何恢复？

如果四个问题都没有回答，说明文字应删除。

### 9.2 命名方式

- 页面和区域：使用稳定名词，如“服务器与邀请”“界面主题”。
- 按钮：使用明确动词，如“复制”“应用”“删除数据”。
- 状态：描述事实，如“处理中”“已复制”，不使用“太棒了”等评价。
- 危险动作：写明对象和后果，不使用孤立的“确定”“执行”。
- 中英文文案必须同时进入 i18n，不在 JSX 中临时硬编码。

### 9.3 禁止内容

- 与任务无关的欢迎语、导语、格言和故事化包装。
- 重复标题含义的副标题。
- 为填补空白而添加的说明。
- 技术实现细节，除非用户需要它来正确输入或诊断连接。

## 10. 响应式原则

- `1200px`：复杂网格开始减少列数。
- `920px`：设置工作区缩窄侧栏，双栏内容准备收敛。
- `760px`：主要单列断点；侧栏转横向页签，卡片内边距使用 16px。
- `560px`：连接页和紧凑手机布局。

手机端检查：

- 页面 `scrollWidth` 必须等于 `clientWidth`；局部表格和页签可在自己的容器内滚动。
- 触摸目标不小于 44px；视觉上的小图标按钮仍保留足够点击区域。
- 输入字号不小于 16px，避免浏览器自动缩放。
- 固定或 sticky 元素不得遮挡页面标题、输入框和错误提示。
- 安全区和动态视口必须适配手机底部手势区与浏览器工具栏。

## 11. 常见反例

| 反例                                      | 正确判断                                             |
| ----------------------------------------- | ---------------------------------------------------- |
| 每个区域都使用独立背景色                  | 使用同一表面系统，通过标题、间距和状态表达差异       |
| 同一页出现三个实心主按钮                  | 选出当前任务的唯一主要动作，其余降为 secondary/quiet |
| 为对齐单个元素添加任意 `margin-top: 13px` | 回到父级布局，用间距令牌和 `gap` 解决                |
| 在 Paperwhite 单独覆盖文字颜色            | 修正语义令牌或组件层级，让所有主题共享规则           |
| 设置页重新写一套 tab CSS                  | 使用 `SettingsWorkspace`                             |
| 卡片标题下固定放一句“在这里管理……”        | 没有说明后果、格式、例外或恢复方式时删除             |
| 删除按钮使用 primary                      | 使用 danger，并提供与风险匹配的确认步骤              |
| hover 时改变边框宽度                      | 保持几何尺寸，只改变颜色、阴影或轻微位移             |
| 行内按钮 hover 时出现独立背景块或描边块   | 保持行结构完整，仅使用语义文字色或图标色反馈         |
| 用 placeholder 代替标签                   | 使用 `Field` 的持久标签，placeholder 仅展示格式      |

## 12. 设计验收

每次 UI 修改至少回答以下问题：

### 信息架构

- 用户进入页面后，能否在五秒内看出主要任务？
- 页面是否只有一个最醒目的动作？
- 内容分组是否来自用户任务，而不是组件或接口名称？
- 是否存在没有真实分组意义的卡片？

### 视觉

- 标题、正文、辅助说明是否形成稳定层级？
- 间距是否全部来自令牌，父级是否使用 `gap` 管理节奏？
- 强调色面积是否克制？
- Lamplight 和 Paperwhite 是否同样清晰，其余三套主题是否没有固定色泄漏？

### 交互

- 键盘能否完成所有操作，焦点是否可见且按预期返回？
- loading、disabled、empty、error、success 是否都有真实状态？
- 手机端是否没有页面级横向溢出，所有触摸目标是否足够大？
- 动效是否服从 reduced motion？

### 文案

- 每段说明是否解释后果、格式、例外或恢复方式？
- 是否添加了与任务无关的导语？
- 按钮是否使用明确动词，危险动作是否写清对象？
